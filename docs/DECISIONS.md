# Integration decisions (30 Oct 2026, approved by Omar)

Submission UI = Zoha's `mobile/` app on main (backend-wired). The Next.js `frontend/` stays only as fallback.

1. **Language:** English default, German toggle (whole UI; patient quotes stay in the original German).
2. **Source click is mandatory:** tapping "source" opens the original letter with the relevant passage highlighted and scrolled into view (not just the bare sentence).
3. **Zoha's newer UI** (AppBar, Help/FAQ, error pages from `origin/mobile-frontend`) is ported onto main's backend wiring. Never ship mock data.
4. **Screen content:** short view, plus a visible "Also relevant" section for P2 (no click needed). Dashboard tab hidden.
5. **Not applicable / not authorised** get their own banner screens (not "Verified").
6. **Trust labels:** use the engine's four: Consistent across letters / Letters disagree / Outdated / Mentioned once (+ Not documented, Not applicable).
7. **Safety core on every clinical screen:** allergies and age/sex always shown.
8. **History tab works:** backend fills `value`/`unit` on numeric facts.
9. **Readable contradiction titles:** no raw passage IDs in titles.
10. **Routing gaps:** weight review, rheumatologist and other unseen roles route sensibly; unknown clinical roles show their own label, never "GP".
11. **Login:** the PIN lock replaces the site password, inside FastAPI. Demo PIN stays **2468**. Audit log may reset on redeploy (accepted for the demo). Login can be switched off with SECOND_LOOK_AUTH=0; off for the demo since 30 Oct.
12. **Hosting:** Docker image builds `mobile/`, FastAPI serves it with an SPA fallback for deep links.
13. **Privacy fixes:** no patient data in browser history state, self-hosted fonts, on-device voices only, mock patient renamed.
14. **English translation under German quotes:** deferred (needs an LLM key); toggle shows UI language only.
15. **Lymph-node item:** stays a documentation note until the medical team decides.
16. **AI reading, LLM primary with a rules veto (owner decision 31 Oct; replaces the earlier "proposes only" design):** when `SECOND_LOOK_LLM=1` + `ANTHROPIC_API_KEY` are set, Claude Haiku 5.5 reads every request (engine/llm.py) in one structured call: `request_kind` (clinical_task | no_task | non_clinical_requester | spam_or_abuse | other_patient), `requester_role` (enum of real role ids), `bundle_ids`, `focus_concepts` (enum of record labels), `reason` (<= 15 words). The cached system prompt states the access policy (clinical requester + care task; relatives, students, social workers, admin, press, insurance, on-behalf, hypothetical roles refused; no role -> no_task) with hand-written few-shot examples. Data only for clinical_task with a role: its role and bundles replace the rules' routing (engine/route.py); non_clinical/other_patient -> not authorised; no_task -> "describe your task" (or "say who you are" without a role); spam -> neutral "no answer" screen; all with 0 facts (engine/llm_gate.py). Deterministic VETO, deny wins on either side: the rules refuse whatever the LLM says on a non-clinical self-identity (lexicon, deny-wins identity, policy, purpose, withdrawn claims), greeting- or injection-only text, or another patient. Latency: the call starts in parallel with the rules, thinking off, effort low, max_tokens 300, deadline 2.5 s from the request's start -> rules result; normalised-text LRU cache. No key / timeout / error / budget stop -> rules only (the full rules gate of item 19). Budget guard engine/llm_budget.py unchanged (`SECOND_LOOK_LLM_BUDGET_EUR`=4, `SECOND_LOOK_LLM_MAX_CALLS_PER_DAY`=3000). Briefing `routing.llm_kind`, `llm_verdict`, `llm_reason`, `llm_ms`, `engine_ms`; the start-up self-test (`EVAL_ON_START=1`) runs the red-team set with the LLM on and prints latency p50/p95.
17. **Task focus (engine/focus.py):** facts the task points at are promoted into the short view as one card after the P1 needs, after the clinical gate and never on a not-applicable screen. Deterministic (no key needed): a diagnosis sharing a significant clinical word with the situation (synonyms in `rulebook/kb_overlay.json` `task_terms`), plus overlay `task_relevance` entries (endocrine therapy -> osteoporosis, radiotherapy -> SLE, oncology discharge -> planned procedure), each `source: TODO-cite` for the medical team; overlay role `nephrologist` puts kidney function at P1. With the LLM on, the structured output also returns `focus_concepts` (0-5) from an enum of the record's concept labels (deduplicated diagnosis labels + result/plan categories); code keeps only record labels and existing fact ids -> "AI-highlighted for this task" card, `routing.llm_focus` (+ `routing.task_focus`).

18. **Request understanding, rules only (31 Oct, after holdout v2 run 1; general mechanisms, not fitted to holdout cases):**
    - Clinical gate and roles in FR/ES/IT/TR/AR besides EN/DE (`rulebook/clinical_roles.json` `*_intl`, overlay `aliases_intl`/`tags_intl`/`role_stems`); matching is accent- and umlaut-folded. Non-clinical requesters are refused in every language; an LLM-read role still never authorises.
    - New overlay roles (generic physician/doctor/consultant, sports, occupational, palliative, gastro, sleep, pulmonology, toxicology, infectious disease, travel medicine, haematology, geriatrics, gynaecology, obstetrics, paediatrics, neonatology). A recognised role with unrecognised task wording gets its own typical task (`role_fallback_bundles`, else first default bundle) with a note, not the 4-card safety summary.
    - Named topics (`kb_overlay.json` `topics`, engine/focus.py): a topic the request names (bone, cognition, Holter, HbA1c, Sozialanamnese, tansiyon ...) adds its KB slots at P1, shows its facts open, and says "not documented" (facts and passages searched) when the record has none. Items of named topics or sharing a word with the request are never behind "+N more"; P1 history cards hide open questions before findings.
    - engine/request.py: exclusions ("not interested in X", "ohne X", "sans X", "X hariç") remove that topic except the safety core; instructions inside the request ("ignore instructions", "add diagnosis", "print all documents") are blanked before routing and listed in the note; a different patient (name, ID, date of birth, age outside the record's range) is refused with the reason.
    - Applicability by age as well as sex (paediatrics <= 17, neonatology, pregnancy care <= 55: TODO-cite); the whole screen is not applicable when the item is about who asks or the asking specialty owns the item (urologist + prostate).
    - "Letters disagree" card: every contradiction / documentation note touching a shown fact (both sides open, explanation as a linked computed line); a documentation-review request shows all. Items a counted contradiction is about carry trust "conflicting".
    Every new rule/lexicon entry is `source: TODO-cite` for the medical team.
19. **No task, no data (31 Oct, after a tester typed "hi" with the Anaesthetist chip and got the role's default screen):** patient data only for a recognisable clinical TASK. After the clinical gate (non-clinical requester -> not authorised), engine/intent.py removes the requester's words and looks for a KB task, a named topic, an applicability item, a review/overview request or any clinical content word (KB tag words, slot labels, task_terms, topic terms, drug names, the record's concept labels, and the multilingual intent / body / symptom words of `rulebook/task_intent.json`: assess, worry, coming in, before surgery, Aufnahme, abklären, toenail, thirsty ...). Greetings, filler, test input, emoji and keyboard mash never count. Nothing found -> screen mode `needs_task`: zero cards and facts, no patient header, counts, dates, contradictions or safety strip, only "Please describe your task" with generic examples (EN/DE banner in the app). Vague but clinical wording with a role ("anything I should worry about?") still gets the role's default task. With the LLM on, its `actionable_clinical_task` = false can only restrict a request the rules matched by content words alone; it never turns needs_task / not_authorised into data. Also: a non-clinical self-description anywhere in the text ("I'm a nurse, well, a journalist really", "I actually deliver pizza") overrides a clinical claim -> not authorised. v1 s07 ("surgeon", role only) now expects needs_task. Clinical words include acute states (bewusstlos, Atemnot, unconscious, chest pain ...) and clearance/fitness tasks (Sportfreigabe, Belastbarkeit, fit to fly ...); the self-description rule applies only to the requester's own identity ("I'm the GP and her daughter asked me" stays clinical); tag fuzzy matching skips function words ("should" is not "shoulder"). Round 2: emergency shorthand requesters (ER doc, ED, A&E, medic, on call, code blue, rapid response / MET, resus, "emergency:"), more acute states (cyanotic, ST elevation, arrest, Herzstillstand); a relative + reporting verb ("the husband called", "die Tochter hat angerufen") is a mention when a clinical requester is present; a self-correction ("Paediatrician... wait, internist", "eigentlich") uses the last role; time/setting tags ("Nacht") do not pull a non-emergency role off its own task; palliative care falls back to the medication/symptom review, urology to the core summary. Round 3, deny wins: a non-clinical identity in the leading role phrase, a first-person self-description or the last self-correction refuses (cleaner, porter, security, director, administrator, CEO, controller, Verwaltung, Geschäftsführer, IT ...), whatever clinical words follow; emergency/team words (code blue, rapid response, MET, resus) never create a requester; a possessive or reporting-verb mention of a relative is not the requester. The optional LLM adds `requester_is_clinical` (restrict only: false -> not authorised). A clear task without any role stays refused but the message asks for the role. RN/LPN/ICU RN are nurses; a person alias beats a setting alias ("Nurse, night duty" is the nurse). Round 4 (stricter gate): a negated or denied clinical claim ("not a doctor", "kein Arzt", "ex-nurse", "Nurse? no, ...") is withdrawn and refuses when no other clinical identity is left; a relational identity ("doctor's wife", "GP's assistant") is not that role; a non-clinical purpose (just curious, housing, insurance claim, court, press, research without ethics) refuses whoever asks; title words (manager, inspector, auditor, officer, director, administrator, ministry ...) win even in "ward manager", "medical director", "medical officer" (refused for the demo; `titles_override` in clinical_roles.json, "house officer" excepted); owner policy `policy.refuse_roles` refuses medical students and social workers (easy to flip; v1 s46/s67 expect data and now fail by policy); typos of non-clinical words are checked before any fuzzy clinical role; role words in ru/uk/zh/ja/pl/el/hi/fa/he and UK/US shorthand (SHO, reg, FY1/2, SpR, ANAESTH, ortho, cardio, attending, Dr.) count; greetings alone get the needs_task screen. Owner decision (31 Oct): no requester role -> no data even when the task is clear ("STAT CT head, any bleeding risk meds?"): the needs_task screen says "Please say who you are (your clinical role) and the task" with examples (`routing.role_missing`); medical students / social workers stay refused by policy. Lexicon: `source: TODO-cite`.

20. **Answer-first screen (owner, 31 Oct; the expected answers are 1-2 sentences per question, our screen showed 9-16 cards and up to ~90 facts):** the results screen opens with a short **Key facts** block, everything else is behind ONE "Show more / Mehr anzeigen" expander (collapsed by default; the Details and History tabs stay). engine/keyfacts.py picks, per P1 need, the single best current answer from the need's own card items, deterministic, no new wording: `current_list` = the current regimen of that class (whole list for `med_current`, max 10); `latest_value` = newest item of the slot map's primary categories (lvef -> lv_function only; one per key for receptors; the same statement worded more completely a few days earlier, e.g. "... (left)", wins); `trend` = every dated value + the calculated change; `plan` = the future planned item; `laterality_finding` = the majority side, with value; `event_history` = the latest episode's best-documented event + its cause; `status_check` = one line per recommendation (no record after X / documented); `list_all` = the 3 items most related to the request words. Plus: age (calculated) + sex + allergies as one safety line; all not-documented P1 needs as one line; the first counted contradiction the screen touches as one line (+N in details); task focus / named topics only with room left and only what no line already shows. At most 8 lines: over that, neighbouring lines of the same KB group are merged (never dropped). Every row keeps its passages (Source opens the letter with the passage highlighted); meds show "since MM/YYYY" (first letter listing the same statement). API: `Briefing.key_facts` + `layout: "answer_first"`, `NeedResult.key`; existing fields unchanged. Start screen: one free-text field ("Who are you and what do you need?"), sent as typed; no role chips, no example chips; the not-authorised / needs-task banners show the plain message without example chips. Measured by `python3 -m eval.keyfacts` (official 15/15 inside key facts, <= 8 lines; v1 synthetic share of answered questions found in key facts). The synthetic scorer (eval/synthetic/run.py) still scores key facts + details (the whole short response, one tap away), so 170/170 stays a regression check of the content; eval/keyfacts.py is the answer-first metric.
21. **Specific questions and accuracy (30 Oct, engine/ask.py; routing guide fallback layer 3):**
    - A question about one thing ("did she ever have a fall?", "Blutgruppe?") that no named topic or bundle tag covers is answered by its KB slot when the lexicon names one (pacemaker -> cardiac_device, smoking, height, blood thinners: guide layer 2), otherwise gets a "Your question: X" card: facts whose own quote holds a search word, else the passages quoted word for word, else "Nothing found for X: none of the N documents contains any of these words: ..." (only letters written by the as-of date are searched). Search words come from `rulebook/ask_lexicon.json` (English -> German, `source: TODO-cite`); a subject without a German entry says the search was limited instead of claiming absence. Administrative facts (case numbers) never answer.
    - A question that names no task (no bundle tag matched) shows only the safety core plus its answers (named-topic or question cards), not the role's whole default view; no "also relevant", no task focus. A task plus a question keeps the task screen and adds the answer card.
    - Planned procedure: plans whose date has passed, reasons for admission in the history section, and plans from letters written after the as-of date are left out. "recommended" is displayed as "recommended" (never "not done": nothing checked that). Open questions / suspicions beside the finding that answered them are dropped from "related". Different measures on one day are listed, not joined with "->".
    - With item 19 (no task, no data): after the clinical gate, a question whose subject the lexicon or a KB slot knows ("does she hav a pacemakr?") counts as a task, and so does a medical-looking subject (-itis, -osis, -ectomy, disease, fracture ...) or a word the letters contain ("does she have sarcoidosis?" -> "Nothing found"). Other scripts count only through the task vocabulary (task_intent.json: антикоагулянты, 抗凝, przeciwzakrzepowe); their phrases get the role's screen, never a "Nothing found" card, since German letters cannot contain them.     - Requester forms (clinical_roles.json): a relative's clinician is that clinician ("the husband's cardiologist", mirror of "doctor's wife"); "<specialty> consult" names a consulting doctor ("cards consult", "endocrine consult"); Polish inflected role words (lekarzem, kardiologiem ...). 22b. **Answer lines: the rules pick, the LLM writes, code verifies (owner, 30 Oct; the expected answers are 1-2 short sentences per question, ~300 characters per situation, our key facts were 6-8 long lines, ~1000):** the default screen is a thin header (age · sex · allergies) plus at most 4 one-sentence ANSWER LINES (engine/answers.py, `Briefing.answer_lines`, `routing.answer_lines_llm`); key facts, cards, history and contradictions sit behind "Show more" (`key_facts` stays in the API).
    - Picking (deterministic): the user's own question first (engine/ask.py question cards, then KB slots a question named); then the P1 slots of each task bundle in KB order (a composite bundle in `rulebook/kb_overlay.json` `answer_composites`, B05 contrast safety, is ONE need of its P1 slots: native CT, metformin, "kidney function not documented"); then named topics; then the other P1 cards (role modifiers). The first need of each bundle / of the topics / every question keeps a seat. A need is skipped when an earlier line already shows it (same facts; same values and words; same episode of an event). An event line adds the quantified cause ("carotid artery stenosis, left, 60%"); a laterality line touched by a counted laterality contradiction carries the minority side ("one letter (...) says right"); not-documented needs are their own line (neighbours merged). Over 4: neighbours of the same KB group and shape are merged (two per line), then the last unreserved needs move to "Show more". A question-only screen shows the header and the answer line(s) only; "Nothing found for X" is shown as written.
    - Writing (optional, `SECOND_LOOK_LLM=1` + key; `SECOND_LOOK_ANSWERS_LLM=0` turns only the writer off): one batched Claude Haiku call per request after routing (cached system prompt with style rules and hand-written few-shot examples on other patients' facts, not the official answers; thinking off, effort low, max_tokens 120 + 90 per line, deadline SECOND_LOOK_LLM_TIMEOUT 2.5 s, budget guard of item 16, cache by need ids + fact ids). The model gets each line's facts (label, attrs, date, status, computed values, follow-up status, not-documented needs, contradiction note) and returns one sentence per line id; it never selects, drops, reorders or adds needs or facts.
    - Verification (code, per sentence, an ALLOWLIST after an adversarial review): the sentence is tokenised (case and accents folded); every token must be in that line's own facts (labels, values, attrs, units, schedules and their meanings, quotes, computed values, statuses, notes, its dates in any rendering) or in a fixed list of connector words (and, of, in, on, as, since, with, about, lost ...; no negations, number words, side words or drug classes). Every number keeps the facts' unit; a value next to a date must be a fact's value of that date; a fact's schedule (1-0-0) must appear and no other; every fact still named; "not documented" only (and always) when the line has a not-documented need, "no later value" only for a latest value; a contradiction note kept; <= 2 sentences, <= 260 characters (70 per item for long regimens). The attacks (number words, swapped dates, unit changes, added drug classes, flipped negation or side, wrong schedules, values of another line, advice) are unit tests (engine/test_answers.py). Failure, timeout, no key, budget stop -> a deterministic template per shape (current regimen, latest value + date, trend + change, event + cause, laterality + minority side, plan + date, list, follow-up status, not documented, composite). Each line records text, needs, fact ids, passages (Source), origin `llm` | `template`, verified.
    - Measured by `python3 -m eval.answers` (templates here: official 15/15 in the answer lines, 4 lines per case; chars per case 354/486/332/581/658 vs expected 201/287/279/466/240 — the templates quote the letters' wording, the LLM sentences are shorter; v1 synthetic 134/144 found questions inside the answer lines); the start-up self-test prints `EVAL: answers (llm): official in-lines x/15, avg chars, llm lines y, rejected z`. The synthetic scorer still scores the whole short response (details one tap away), so 170/170 stays the content regression check.

      2. *Each concept once.* Facts are deduplicated by concept (`cited.concept`: the same drug + dose, the same value + unit + side, else the same category + label without parentheses and filler words: "Known contrast media allergy" == "Contrast media allergy (nausea, vomiting) at last examination"). The required appendix skips a fact whose concept the sentence already shows (live: HbA1c twice).
      3. *Only what the question needs.* The prompt says so (pick only facts that answer this question, prefer "not documented" over loosely related facts, each finding once, the majority side) with few-shot examples of our own (not the official answers), including a drug-safety question. Code drops loose picks: an allergy unless the request names allergies or that allergen or a required fact asks for it (live: gentamicin -> contrast allergy x3), a family / social / general-condition note unless the request names it (live: Vorsorge -> "No known relevant family history; well supported by her family"). A **drug-safety map** (`engine/drug_safety.py`, TODO-cite for the medical team: aminoglycosides such as gentamicin, vancomycin, NSAIDs, iodinated contrast, metformin) adds the newest metformin / diabetes / contrast-allergy facts as required facts, the same way as a bundle's P1, and "kidney function" as a not-documented topic when no fact covers it. It only chooses among the letters' facts; it never adds a value.
      4. *One natural sentence, not a semicolon list.* A model template that is a list of facts ("{F1}; {F2}; {F3}.") or that needed a change (1-3) is rewritten by code from the same facts (`cited.natural`): "She takes A and B and has C; also documented: D and E (14 June 2015)" (drugs as name + dose + schedule, conditions, then other facts with their dates, a run of equal dates once), then "Not documented in the letters: X". Connector words only; every value still comes from the facts. A model sentence that is already a sentence is kept as written (plus flags). Without required facts, model facts beyond 300 characters go to "Show more"; the list form remains only for the official appendices that are longer by nature.
      5. *The fallback uses the request's topic.* `request_topic` no longer splits on abbreviation dots ("i.v."); the drug-safety map's topic answers a drug request ("Notärztin, gleich Gentamicin i.v." -> "She takes metformin (Glucophage) 1000 mg 1-1-1 and has diabetes mellitus type II. In the fallback, a recognised role without a matched task bundle and without a direct question answers "Not documented in the letters: <its topic>" instead of the role's general cards (live: a Kardiologe timeout got the 2015 follow-ups); the rules' own question lines and slots the request names stay.

What the model still leaves out is appended as before (one natural second sentence), so 15/15 does not depend on the model.
